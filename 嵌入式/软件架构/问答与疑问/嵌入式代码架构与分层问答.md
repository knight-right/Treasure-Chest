## 面试问题

### 1. HAL 库是在哪一层被调用的？

**文档作答**：HAL 是在 Core 层被调用，用于初始化。

**参考答案**：

- HAL 属于 Driver 层，被 Core 层调用。
- 实际上 Driver 是对硬件（寄存器）的抽象，Core 层是对 MCU（外设）的抽象。

### 2. OS 实现 APP 之间信息传递的方式有哪些？

**文档作答**：通过队列、信号量、互斥量、回调函数。

**参考答案**：

1. 队列（Queues）、信号量（Semaphore）、消息缓冲区（Message Buffers）
2. 事件组（Event Groups）、共享变量（Shared Variables）、回调机制（Callback Mechanism）

### 3. OS 实现 APP 和 BSP 之间信息传递的方式有哪些？

**文档作答**：队列、信号量、互斥量、回调函数。

**参考答案**：

1. 队列（Queues）、信号量（Semaphore）、事件组（Event Groups）
2. 回调函数（Callback Functions）、共享变量（Shared Variables）、中断处理（Interrupt Handling）

## 问题解答

### 1. OS 和 Core 的连接主要在干什么？完成操作系统的初始化？

OS 会和 Core 里的 SysTick 中断回调产生联系：SysTick 回调里会触发 PendSV 中断，产生 OS 的任务切换。同时，任务切换过程中使用前导零指令在一堆任务里找到最高优先级的任务，这也是 Core 层提供的。它用于给 OS 提供调度接口，应用层和底层不产生直接联系，通过统一的中间接口调用，使其完全解耦。

### 2. BSP 发送到 RTOS 的数据都存储在缓冲区里吗？有没有其他方式？

APP 可以直接向 BSP 驱动注册回调函数，BSP 数据准备好后直接执行对应的操作，课程后面的 AHT21 驱动就是这样做的。

### 3. BSP 层的作用是什么？

它实现了 MCU 和板上外设器件（比如 MPU6050）的通信与交互过程，一般包含详细的 MCU 与板上器件的通信逻辑。比如和 MPU6050 通信可以用硬件 IIC，也可以用软件 IIC，还可以用硬件 IIC + DMA。IIC 是每个 MCU 都能提供的，所以 IIC 本身不需要写进 BSP，BSP 只是调用 Core 层提供的 IIC 接口来完成自己的事情。以此类推，用于 IIC 通信的引脚也由 MCU 提供，GPIO 初始化这些也不应该包含在 BSP 里。

所以 BSP 应该是纯粹描述 MCU 和板上器件通讯的代码，这些代码既能在 STM32 上用，也能在 GD32 上用，还能在 Linux 上用。只有写出这样的程序才有高移植性，换公司后这些逻辑才能跟着你走，尽可能屏蔽硬件的差异性。

### 4. BSP 层的目的之一是把硬件管理和业务逻辑完全分开吗？按键的短按、长按算哪一类？

BSP 层本来就和业务层隔离，它往往包含 HAL Driver 层和 Handler 层：

- **HAL Driver 层**：非常直接的硬件操作。按键按下（中断触发）被检测到，这部分是按键的硬件管理。
- **Handler 层**：有操作系统时才有。把「按下的时间、按下还是松开」告诉需要按键信息的 APP，这部分已经与硬件无关，主要解决适合操作系统的信号传输方式、栈隔离、调用链确定性的问题。到这里 BSP 的任务基本做完。

APP 收到按键按下的时刻和类型后，自己决定要做什么，比如按下按键打开一个继电器，这才是纯粹的业务逻辑。

这样划分还和公司内的分工有关。写 APP 的人和写 BSP Driver 的人很可能不是同一个人，BSP Driver 需要提供的是最原始的数据和最高效、稳定的硬件接口（最好是非阻塞的），写 APP 的人根据原始数据判断情况。以按键为例，BSP 层通过线程间通信把按键数据按顺序、完整地发给 APP，由 APP 结合业务去理解什么是长按、什么是短按。按键除了短按、长按，还可能有三连按、四连按，全写进 BSP 会非常臃肿，而且永远无法穷尽；不同使用者对长按和短按的理解也不一样，更不可能由 BSP 来区分。

### 5. ymodem、modbus、PID 这类和硬件强相关的协议或算法，放在 BSP 层吗？

不是，这些更多放在中间件层。以 Ymodem 在串口收发上的应用为例：UART 另一端如果接的是蓝牙模块，蓝牙可以抽象为一个板上外设，蓝牙的控制（比如串口收发 AT 指令）是 BSP 的一部分。但 BSP 通过蓝牙收到手机发来的 Ymodem 数据后，不应该在 BSP 里处理，因为串口上能走的协议不只有 Ymodem，还有 Xmodem 和自定义协议，BSP 无法穷尽。

这种场景下，BSP 顶多向 APP 要一块 buffer，把串口断帧（空闲中断等）后的数据放进缓冲区，然后通知 APP 去取。APP 再去缓冲区解析数据，此时可以选择用 Ymodem（中间件）或 Modbus（中间件）来解析。

### 6. RT-Thread 的设备框架放在这个架构的哪个位置？

提问者的理解是：设备框架就是片上外设驱动框架，对外设进行管理。回答是：它其实就是 BSP 层里的 Handler 层，见上面第 4 问，后面的驱动作业也会详细涉及。

### 7. 会为每一个器件或设备都建立一个 task 吗？会不会浪费内存和调度资源？

会为**某一类**设备建立一个或多个 task。

**「一类」的情况**：比如一个专门管理温湿度类设备的 BSP 程序，可以同时管理 AHT21、DHT11。温度是大惯性参数，不需要一秒读几千次，一两秒读一次即可，所以两种器件的管理流程一样。它们的区别只在 HAL 驱动不同，但最终都会提供读取温度、读取设备 ID 的接口给 Handler 层。因此 Handler 是通用的，只需要写出符合 Handler 层接口要求的 HAL 驱动，Handler 层代码可以无限复用。

**多个 task 的情况**：电机是非常高速的设备，读取电机电压电流的 APP 需要超快的响应。只有一个线程时，线程在采集电压的过程中无法立刻回到信号量或队列接收函数去响应调用，所以会用两个线程：一个专门响应外部 API 调用，另一个专门做电压采集。更明显的例子是课程后面的音频播放 Speaker 高级驱动。

### 8. 电机这种既有数据采集又有控制输出的设备，当作整体处理还是输入输出分开？

如上面所说，这种情况一个 task 处理不了，Handler 层会用至少 2 个线程来保证高响应性（并发）和实时性。

### 9. 把 BSP 层抽出来，付出了什么代价？

提问者想到的代价：一是增加了调用的复杂度，但不知道如何量化，对不同主频的芯片影响多大；二是用函数指针解耦增加了 RAM 占用，32 位机器上一个指针占 4 字节；三是不确定还有没有其他代价。

**答**：

- **调用复杂度**：指针嵌套确实增加了寻址次数，但代码结构更容易理解，解耦明确，移植性强。STM32F10x 在 72 MHz 主频下，C 程序执行一条指令的时间可认为是 10 ns～100 ns。一次指针跳转是 2 条指令，层级最多按 4 层指针算，平均约 200 ns，对运行速度影响非常小，而且 72 MHz 已经算很慢的主频。课程后面还会讲用 sct 文件指定驱动链接区域，把常用 IO 通过固定地址确定下来，直接用立即数访问，比函数嵌套还快。
- **RAM 占用**：同样可以通过固定链接地址，在后期把这些指针消耗极大减少甚至消除（如果有必要这么极端的话）。
- **真正的代价**：对开发人员水平要求较高。
