## 题目

### 1. 从源码到可执行文件经过哪些步骤

- [ ] 能脱稿讲清楚
- **来源**：[[嵌入式/面经/面试记录/智元机器人-嵌入式-二面|智元机器人-嵌入式-二面]] 第 14 题。
- **口述版答案**：四步。
  - 预处理：展开宏、处理 `#include` 和条件编译、去掉注释，得到 `.i` 文件。
  - 编译：做语法和语义检查、优化，把 C 代码翻译成汇编，得到 `.s` 文件。
  - 汇编：把汇编翻译成机器码，得到可重定位的目标文件 `.o`。这时函数和全局变量的地址还没确定。
  - 链接：把所有 `.o` 和库文件合并，解析符号引用，按链接脚本给各个段分配地址并完成重定位，得到 ELF 格式的可执行文件。
  - 嵌入式多一步：用 `objcopy` 把 ELF 转成 `.bin` 或 `.hex` 再烧录。
- **常见追问**：
  - 对应的 gcc 选项：`-E` 只预处理，`-S` 到汇编，`-c` 到目标文件。
  - 链接脚本做什么：规定 Flash 和 RAM 的起始地址和大小，以及代码段、数据段各放在哪里。
  - `undefined reference` 出在哪一步：链接。声明了但找不到定义。
  - 静态库和动态库的区别：静态库在链接时把代码拷进可执行文件；动态库在运行时加载。裸机 MCU 上只用静态库。
  - 启动文件做了什么：设置栈指针和向量表，把 `.data` 的初值从 Flash 拷到 RAM，把 `.bss` 清零，再跳到 `main`。
- **易错点**：把“编译”和“汇编”两步说成一步，或者顺序说反。
- **深入阅读**：[[基础知识/编译与调试工具/编译与调试工具索引|编译与调试工具]]

### 2. bin 和 elf 文件的区别

- [ ] 能脱稿讲清楚
- **来源**：[[嵌入式/面经/面试记录/智元机器人-嵌入式-二面|智元机器人-嵌入式-二面]] 第 15 题。
- **口述版答案**：
  - `.elf`：链接器直接输出的文件。除了代码和数据，还带有文件头、各段的加载地址、符号表和调试信息。
  - `.bin`：纯粹的内存镜像，只有要写进 Flash 的原始字节，不带地址和符号。它由 ELF 用 `objcopy -O binary` 提取出来。
  - 用途：调试用 `.elf`；量产烧录、OTA 升级、Bootloader 加载用 `.bin`。
  - 因为 `.bin` 不带地址，烧录时必须自己指定写到哪个地址。
- **常见追问**：
  - `.hex` 是什么：文本格式，每行带地址和校验，烧录时不用另外指定地址。
  - ELF 文件比 bin 大很多，是不是程序占用很大：不是，多出来的主要是符号和调试信息，不会烧进芯片。
  - Keil 生成的 `.axf` 是什么：也是 ELF 格式的带调试信息的文件。
  - 怎么看程序实际占多少 Flash 和 RAM：用 `size` 工具看 text、data、bss 的大小，或者看 map 文件。
- **易错点**：烧录 `.bin` 时地址填错，程序不运行。应用程序前面有 Bootloader 时尤其要注意偏移地址。
- **深入阅读**：[[基础知识/编译与调试工具/编译与调试工具索引|编译与调试工具]]

### 3. gdb 调试时加载哪种文件

- [ ] 能脱稿讲清楚
- **来源**：[[嵌入式/面经/面试记录/智元机器人-嵌入式-二面|智元机器人-嵌入式-二面]] 第 16 题。
- **口述版答案**：
  - 加载 `.elf`，而且编译时要加 `-g` 带上调试信息。
  - 原因：gdb 要靠符号表和调试信息把地址对应到函数名、变量名和源码行号。`.bin` 里只有机器码，没有这些。
  - 嵌入式上的流程：电脑上运行 gdb server（OpenOCD 或 J-Link GDB Server）连接调试器 → `arm-none-eabi-gdb xxx.elf` → `target remote` 连上 server → `load` 把程序下载到芯片 → 设断点、运行。
- **常见追问**：
  - 常用命令：`break` 设断点、`continue` 继续、`next` 和 `step` 单步、`print` 看变量、`backtrace` 看调用栈、`x` 看内存、`info registers` 看寄存器。
  - 芯片里烧的是 bin，还能调试吗：能，只要手上有对应版本的 elf 提供符号，gdb 连上后不执行 `load` 即可。
  - 开了 `-O2` 调试时变量显示被优化掉怎么办：调试时用 `-Og` 或 `-O0`。
- **易错点**：烧进芯片的固件和 gdb 加载的 elf 不是同一次编译的产物，断点和行号会对不上。
- **深入阅读**：[[基础知识/编译与调试工具/编译与调试工具索引|编译与调试工具]]

### 4. CMake 和 Makefile 的区别

- [ ] 能脱稿讲清楚
- **来源**：[[嵌入式/面经/面试记录/智元机器人-嵌入式-二面|智元机器人-嵌入式-二面]] 第 17 题。原帖只写了这两个词，没写具体问法。
- **口述版答案**：
  - Makefile 是给 `make` 直接执行的构建脚本，由一条条规则组成：目标、依赖、命令。`make` 比较文件修改时间，只重新编译改动过的部分。
  - CMake 不直接编译，它是生成构建脚本的工具：在 `CMakeLists.txt` 里描述有哪些目标、用哪些源文件、依赖哪些库，CMake 据此生成 Makefile 或 Ninja 工程，再由它们去编译。
  - 区别：Makefile 要手写规则和依赖，工程大了难维护，也和平台绑定；CMake 抽象层次更高，跨平台，能自动处理头文件依赖和库的查找。
  - 嵌入式交叉编译时，CMake 用一个工具链文件指定 `arm-none-eabi-gcc` 等工具。
- **常见追问**：
  - Makefile 里几个自动变量：`$@` 是目标，`$<` 是第一个依赖，`$^` 是所有依赖。
  - `.PHONY` 是什么：声明伪目标，比如 `clean`，它不对应真实文件。
  - CMake 的基本用法：`cmake -B build` 生成，`cmake --build build` 编译。常用命令有 `add_executable`、`add_library`、`target_link_libraries`、`target_include_directories`。
  - 改了头文件，为什么包含它的源文件没重新编译：手写的 Makefile 里没有把头文件列为依赖。
- **易错点**：说成“CMake 是用来替代 make 的”。CMake 生成构建脚本，最后干活的仍是 make 或 ninja。
- **深入阅读**：[[基础知识/编译与调试工具/编译与调试工具索引|编译与调试工具]]
