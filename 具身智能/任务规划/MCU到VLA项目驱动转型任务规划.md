> 以现有 MCU 与设备开发经验为起点，围绕一个机械臂项目，依次完成“跑通示例 → 理解与改造 → 接入学习策略 → 评估与作品集”。主攻机器人软件与系统开发岗位，并用训练、推理和实验成果逐步接近机器人学习与 VLA 应用方向。

## 1. 目标、范围与执行原则

### 职业目标

| 方向 | 一年内的定位 | 用什么证明能力 |
| --- | --- | --- |
| 机器人软件、机械臂应用与系统开发 | 主攻岗位 | ROS 2 接口、动作执行、日志与异常处理、可复现项目 |
| 机器人学习应用、策略接入与部署 | 有成果后重点争取 | 示教数据、训练与推理、动作适配、评估与失败分析 |
| VLA 算法研发 | 进阶探索 | 深度学习基础、模型理解、训练实验、数据与泛化分析 |

三个方向是相邻的职业选择。第一年的完成标准是形成可解释、可修改、可复现的能力证据；是否冲刺算法岗，再结合个人兴趣、岗位要求和面试反馈决定。

### 项目范围

- **主项目名称：机械臂 AI 控制系统。**
- 第一项任务：在固定机位的仿真桌面中，把一个方块移动到指定区域；先跑通机械臂运动，再推进抓取与放置。
- 初始范围：一个机械臂、一个简单夹爪、一种物体、一项任务。真机与灵巧手扩展排在仿真闭环之后。
- 初期允许读取仿真中的物体真值位置，作为程序控制基准；后续视觉策略的效果单独评估。
- 已有 MCU、通信、设备调试经验继续积累。RM65、SG100 等已有项目可作为后续接口扩展线索，是否接入取决于硬件可用性、SDK 和实际验证结果。

### 执行原则

1. 先运行一个小示例，再解释关键流程，每次只改一个功能。
2. 遇到具体问题时补对应知识，同时保留少量连续的基础学习。
3. 每周完成一个小成果：能运行的功能、可复现的修复、一次有结论的实验都算。
4. AI 用于读代码、排错和讨论；关键模块应能自己解释、修改和验证。
5. 一年只持续迭代这个主项目。文章、视频、架构说明从项目成果中整理。
6. 月份是建议节奏。未通过阶段验收时，先修复闭环，再缩减后续扩展。

## 3. 主项目的四个版本

| 版本 | 需要完成的闭环 | 交付物 | 完成判据 |
| --- | --- | --- | --- |
| V0：复现示例 | 加载模型 → 执行动作 → 看到结果 | 环境记录、启动命令、第一段演示 | 重启后能按记录再次运行，并能找到动作入口 |
| V1：理解与改造 | 任务参数 → ROS 2 接口 → 仿真执行 → 状态与日志 | 自己修改的功能、动作记录、失败记录 | 能改变目标或轨迹，解释关键数据和代码位置 |
| V2：学习策略接入 | 观测与示教 → 数据检查 → 训练 → 推理 → 控制 → 评估 | 数据说明、模型权重、配置、评估报告 | 在匹配的任务与本体上重复评估，报告成功与失败 |
| V3：作品集 | 环境恢复 → 一键启动 → 任务演示 → 结果说明 | GitHub 项目、README、视频、简历材料 | 按文档从干净环境复现，能讲清个人贡献与限制 |

VLA 是 V2 的可选扩展：先确认模型支持的输入、本体与动作空间，再验证不同语言指令是否对应不同执行结果。关键词匹配、写死动作或只输出文本的演示，应如实标注其实现方式。

## 5. 每月任务清单

### 第 1 月：建立环境，跑出第一个结果

- [ ] 记录现有 WSL2 与 Ubuntu 24.04 的版本、发行版名称和资源情况；按[[基础知识/Linux与Shell/实操及实现效果/WSL2与Ubuntu24.04开发环境规划|环境规划]]验收网络、文件交换和基础工具，继续使用现有发行版。
- [ ] 安装或核对 ROS 2 Jazzy，运行官方 talker / listener 示例；记录实际安装来源、版本和命令。
- [ ] 建立项目代码目录和 Git 仓库；完成一次修改、提交、查看差异，先在本地管理。
- [ ] 通过 WSLg 运行一个可视化或仿真最小示例，保存截图或短视频；记录环境依赖并导出发行版备份，GPU 可用性单独验收。

**边做边学：** Linux 文件与进程、终端、Git 基本操作、Python 函数与文件读取。基础阅读围绕当周问题展开。

**验收：** 重新进入 WSL2 后能按笔记运行示例；能说明两个 ROS 2 节点如何通信，并分别记录图形显示与 CUDA 检测结果。此时不要求模型训练或完整 VLA 演示。

### 第 2 月：让仿真机械臂动起来

- [ ] 选定一个许可清晰、依赖适合 Ubuntu 24.04 与 ROS 2 Jazzy 的轻量机械臂示例，记录仓库、许可证、commit 和启动命令。
- [ ] 优先验证 MuJoCo 的模型加载与关节运动；先验收最小场景，再使用复杂任务场景。
- [ ] 能读取关节状态，并通过修改目标关节值执行一次可观察的动作。
- [ ] 完成一段固定动作或到达指定位置的演示，写出从入口脚本到动作执行的主要调用关系。

**边做边学：** Python / NumPy、关节与连杆、角度与弧度、基本坐标系。URDF 与 MuJoCo 的 MJCF 分别理解，实际转换作为独立工作验证。

**验收：** 能说明状态、目标和执行接口；重置场景后能重复演示。如果图形性能不足，先降低画面复杂度或离屏记录，问题仍无法解决时再换经过验证的轻量示例，并记录原因。

**阶段检查 A：** 已形成 V0；能够复现，也能找到后续要修改的位置。

### 第 3 月：读懂一段流程，完成一次实际改造

- [ ] 梳理模型加载、观测读取、动作生成、仿真步进和结果记录五个位置。
- [ ] 选一个改动：修改目标位置、动作速度、轨迹点或夹爪动作；只选一个作为本月主任务。
- [ ] 保存修改前后演示与 Git 差异，说明改变了什么、为什么有效。
- [ ] 开始项目日志，记录至少一个真实问题的现象、排查过程和验证结果。

**边做边学：** C++ 工程阅读、Python 模块、矩阵与齐次变换。只深入当前代码实际涉及的部分。

**验收：** 能自己再次修改同类参数或逻辑，并解释结果变化。

### 第 4 月：建立 ROS 2 任务与动作接口

- [ ] 将任务入口、仿真执行、状态输出分成职责清晰的模块，使用 ROS 2 节点或适合当前项目的进程组织方式。
- [ ] 选择合适的话题、服务或动作接口，完成目标输入、执行反馈与完成结果的传递。
- [ ] 统一坐标系、角度单位、关节顺序和动作含义，写出接口说明。
- [ ] 让目标位置和动作参数可配置；使用状态、超时与错误记录说明任务当前处于哪个环节。

**边做边学：** ROS 2 参数与 launch、tf2、正逆运动学、轨迹执行。先用可靠的现成求解器理解输入输出。

**验收：** 修改配置后可运行同类任务；能沿日志定位一次未完成的执行。ROS 2 应用层负责组织任务，设备内部的控制环职责单独说明。

### 第 5 月：建立数据与回放，并提前接触训练

- [ ] 记录一段匹配任务的数据，至少说明时间戳、关节状态、动作、任务标识与回合边界；使用视觉时再同步图像。
- [ ] 回放数据，检查状态和动作是否对应，是否存在缺失、错序或单位问题。
- [ ] 用 PyTorch 完成一个小型监督学习练习，理解张量、前向计算、损失、反向传播和权重保存。
- [ ] 确定下一阶段所用的任务、本体、数据与训练算力；公开数据必须核对观测和动作定义，不能直接当作任意机械臂可用的数据。

**验收：** 能展示一段数据及其回放，并解释每个字段；小模型能够保存、加载和输出结果。少量样本只用于流程检查，不据此判断策略能力。

**阶段检查 B：** 已形成 V1；任务可运行，接口可解释，数据能够检查与回放。

### 第 6 月：跑通一种模仿学习策略

- [ ] 选择 ACT 等一种模仿学习方法，核对其示例与当前任务、本体和数据的兼容性。
- [ ] 为训练环境单独锁定 Python、PyTorch、LeRobot 和相关依赖；先完成少量数据的运行检查。
- [ ] 完成一次正式训练或匹配示例复现，保存配置、数据版本、代码 commit、随机种子和权重。
- [ ] 加载权重运行推理，记录输入输出、耗时和第一次任务评估结果。

**算力安排：** 优先在 WSL2 中验证并使用本机 NVIDIA GPU，完成驱动可见性、PyTorch CUDA 和一次实际张量运算检查后，再按显存调整模型、图像尺寸和 batch size。CPU 保留数据检查与小实验用途；本机资源不足时，再评估其他 GPU 训练资源。

**验收：** 能解释图像或状态怎样变成动作，权重可以重新加载；训练完成、任务成功分别记录。

### 第 7 月：把策略接入控制链路

- [ ] 为策略明确图像尺寸、状态顺序、归一化、动作单位、关节顺序与控制频率。
- [ ] 通过已有 ROS 2 接口执行策略动作，验证限位、异常输入、超时与任务停止的行为。
- [ ] 记录任务标识、策略版本、推理耗时、执行状态和结果，能够回看一次完整执行。
- [ ] 若训练与控制在不同进程或机器，先验证离线权重或动作回放，再实现最小推理服务接口；明确时间戳、请求对应关系与超时处理。

**验收：** 形成“观测 → 策略 → 动作接口 → 仿真执行 → 结果记录”闭环。若涉及真机，仿真验证与实机验证分开标记。

### 第 8 月：用实验改进一个问题

- [ ] 固定一组评估条件，按完整任务回合划分训练与评估数据，避免同一回合的相邻画面跨集合。
- [ ] 在时间允许时，对同一任务设置重复执行 20 次，记录成功次数、完成时间和失败类别；同时保留初始状态与随机种子。
- [ ] 针对一个主要失败原因，只改变一个因素，例如示教质量、观测处理、动作尺度或执行频率。
- [ ] 按相同评估条件比较改进前后，并额外检查改变物体初始位置后的表现。

**验收：** 报告包含执行次数、成功定义、比较条件和失败案例。训练损失、固定场景表现、变化场景表现分别说明；20 次是个人项目的起步评估规模。

### 第 9 月：按成果选择 VLA 验证或继续巩固

- [ ] 检查 VLA 扩展条件：现有策略闭环可运行、数据可用、模型与本体动作空间可适配、训练或推理算力有着落。
- [ ] 条件满足时，运行一个兼容的预训练 VLA 示例，梳理视觉、语言、状态与动作的关系；不从头训练大型模型。
- [ ] 选择至少两种可区分的任务指令，检查是否发生相应的目标或动作变化，并记录支持范围和失败情况。
- [ ] 条件尚未满足时，把本月用于已有策略的可靠性、数据质量与接口完善，并记录延后的原因。

**验收：** 有一份可解释的 VLA 实验记录，或一个经重复评估的策略改进版本。没有接入 VLA 时，作品集如实写为模仿学习与机器人系统项目。

**阶段检查 C：** 已形成 V2，具备真实的训练或复现、策略执行与评估证据。

### 第 10 月：把项目整理成作品

- [ ] 整理模块与入口，保存依赖版本、配置、模型或数据获取方式；处理运行中依赖的本地绝对路径。
- [ ] 完成 README：任务、环境、运行步骤、个人贡献、结果、失败案例、限制与资料许可。
- [ ] 在新的 Python 环境或从备份另行导入的 WSL2 发行版中，按文档复现最小示例与项目演示。
- [ ] 整理一段主演示视频和关键截图，清楚标出仿真或真机、程序控制或学习策略；准备可发布的仓库内容。

**验收：** 项目能够被按文档运行，演示与实验结果对应。公开前检查代码、模型与数据的许可和归属，工作项目内容按可公开范围整理。

### 第 11 月：让作品支持求职

- [ ] 按机器人软件、学习策略应用等方向筛选 5—10 个岗位，整理“要求—已有证据—待补项”。
- [ ] 写项目简历，明确独立完成、协作完成和使用开源实现的部分。
- [ ] 练习 5 分钟整体讲解，并准备深入解释一个系统问题和一个实验问题。
- [ ] 根据匹配程度定向投递，记录岗位、日期、进展、面试问题与反馈。

**验收：** 能用代码、演示和实验结果支持简历描述；用反馈调整后续任务。

### 第 12 月：复盘并确定下一阶段

- [ ] 汇总环境搭建、控制接口、数据、训练、部署和评估各自达到的程度。
- [ ] 按求职反馈选择一个最影响目标岗位的短板，完成一项针对性改进。
- [ ] 比较继续积累、转入机器人软件岗位、进一步冲刺机器人学习算法三个选择。
- [ ] 写下一阶段 3 个月计划，保留最有效的项目方向与学习节奏。

**验收：** 有清楚的能力证据和下一步选择。跳槽依据岗位匹配度、实际机会与个人条件决定。

## 6. 每周执行与月度调整

| 时间 | 做什么 | 留下什么 |
