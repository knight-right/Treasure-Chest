# G010/SC235 GMSL 相机三路显示适配总结

记录时间：2026-07-08  
设备平台：Jetson / L4T 5.15.148-tegra  
相机链路：G010/SC235 相机 -> MAX96717 串行器 -> MAX96724 解串板 -> Jetson CSI  
最终目标：解串板 A/B/C 三个口各接一个相机，两根 CSI 线都接入 Jetson，三路同时有画面，并在画面右上角显示帧率。

## 1. 最终状态

当前已经实现：

- 三个 V4L2 视频节点存在：`/dev/video0`、`/dev/video1`、`/dev/video2`。
- 三路可同时显示画面。
- 每路画面右上角显示帧率。
- 相机采集帧率约 `30 fps`。
- 当前显示帧率限制为 `5 fps`，用于规避三路全速显示导致设备卡死的问题。
- 运行期间内核日志没有持续的 `timeout`、`CHANSEL`、`CSIMUX` 错误。

当前启动脚本：

```bash
/home/jetson/Desktop/100.xcDeserializer4.0.01/g010_adapt/show_g010_3cams.sh
```

当前停止脚本：


## 3. 从单相机到三相机的调试路线

### 3.1 起点：先让一个口出图

一开始不是直接做三路，而是先以单个相机口作为起点，调通一条完整链路：

```text
G010/SC235 -> MAX96717 -> MAX96724 -> CSI -> V4L2 -> GStreamer 显示
```

调试过程中保留过多份原始帧：

```bash
g010_adapt/captures/g010_d_uyvy_30.raw
g010_adapt/captures/g010_uyvy_30.raw
g010_adapt/captures/g010_srcvc0_ctrl2_uyvy_30.raw
g010_adapt/captures/g010_lanepol6_uyvy_30.raw
```

这些文件说明当时反复验证过：

- UYVY 数据格式是否正确；
- 不同 source VC / destination VC 是否正确；
- 不同 CSI controller 是否能接到帧；
- lane polarity 对画面是否有影响；
- 单路能否稳定抓 30 帧。

### 3.2 单路稳定后扩展到 A/B/C 三路

单路出图后，下一步把 device tree 从单路扩展到三路：

- VI `num-channels = <3>`；
- NVCSI `num-channels = <3>`；
- 添加三个 sensor 节点；
- 添加三个 VI endpoint；
- 添加三个 NVCSI channel；
- 为每路设置 `port-index`、`bus-width`、`vc-id`；
- 为 MAX96724 增加每路的 `src-vc`、`dst-vc`、`dst-csi-ctrl`。

当前三路设计：

| 路 | Sensor 地址 | 输入/输出设计 |
| --- | --- | --- |
| A | `9-0010` | `src-vc=0` -> `dst-vc=0`，`dst-csi-ctrl=1`，4 lane |
| B | `9-0011` | `src-vc=0` -> `dst-vc=1`，`dst-csi-ctrl=1`，4 lane |
| C | `9-0012` | `src-vc=0` -> `dst-vc=0`，`dst-csi-ctrl=2`，2 lane，`lane_polarity=6` |

这里的关键是：A/B 两路共用一个 CSI controller，所以必须用不同的 destination VC；C 路走另一个 CSI controller。

### 3.3 三路节点出现后再做显示脚本

三路 `/dev/video*` 出现后，没有直接上三路全速显示，而是先做了分层验证：

1. 逐个节点抓帧；
2. 逐个节点 GStreamer 转换到 `fakesink`；
3. 两两并发验证；
4. 三路窗口显示；
5. 三路显示加帧率；
6. 限制显示帧率，避免 Jetson 卡死。

## 4. 遇到的问题和解决办法

### 问题 1：资料里没有现成的 G010/SC235 三路驱动

现象：

- 解串板资料和已有驱动更偏向其他传感器组合。
- 当前相机是 G010/SC235 + MAX96717，需要单独适配。

原因：

- Jetson 需要 sensor driver、serializer/deserializer driver、device tree、media graph 同时匹配。
- 不能只靠普通 USB 摄像头那种方式直接打开。

解决：

- 基于资料包里的 MAX96724 / MAX96717 驱动框架做二次适配。
- 新增 `z_g010_sc235_96717.c` 和 `z_g010_sc235_96717_mode_tbls.h`。
- 在 device tree 中声明 G010/SC235 的 sensor 节点、GMSL link、VC 映射和 CSI 映射。

验证：

- `media-ctl -p -d /dev/media0` 能看到 `z_g010_sc235_96717` sensor。
- `/dev/video0`、`/dev/video1`、`/dev/video2` 能正常出现。

### 问题 2：一开始只能按单路思路调，不能直接三路并发调

现象：

- 三路同时配置时，如果某一路 VC、lane、CSI controller 配错，表现可能只是没有画面、绿屏或 VI 报错。
- 很难直接判断是哪一路错。

原因：

- GMSL 解串板内部有链路、pipe、VC、CSI controller 多层映射。
- 任意一层配置错都会影响最终画面。

解决：

- 先从单个口、单个 `/dev/video*` 开始。
- 单路能抓到 UYVY 原始帧后，再扩展到三路。
- 保留多个 raw 抓帧文件，便于比较不同配置。

验证：

- 单路抓帧文件存在，例如 `g010_d_uyvy_30.raw`。
- 后续三路扩展基于单路已验证过的 UYVY 1600x1200 30fps 配置。

### 问题 3：视频格式如果按错，会出现满屏绿色

现象：

- 运行早期显示脚本时，画面可能出现满屏绿色。

原因：

- 相机输出是 UYVY/YUV 类数据。
- GStreamer caps 或转换链路如果按错格式，显示端会把数据错误解释。
- 绿色画面通常不是“完全没数据”，而是像素格式或同步配置不匹配。

解决：

- 固定 V4L2 caps：

```text
video/x-raw,format=UYVY,width=1600,height=1200,framerate=30/1
```

- 显示前通过 `nvvidconv` 转成 Jetson 显示端更稳定的 NVMM NV12：

```text
nvvidconv ! video/x-raw(memory:NVMM),format=NV12,width=1600,height=1200 ! nveglglessink
```

验证：

- 三路画面都能显示真实场景。
- 不再是固定纯绿色画面。

### 问题 4：绿色画面偶发，不只是 GStreamer caps 问题

现象：

- 修正 UYVY caps 后，绿色画面有时仍可能偶发。
- 特别是在多路启动、重复打开关闭相机时更明显。

原因：

- 早期逻辑在 stream-on 阶段可能重新初始化 MAX96717。
- 多路并发启动时，某一路重新初始化 serializer 可能影响同一解串器上的其他链路状态。

解决：

- 把 MAX96717 的 G010 初始化前移到 probe 阶段。
- stream-on 阶段不再重复执行 `max96717_apply_g010_init()`。
- 每个 link 在 probe 时隔离配置，避免多路同时开始取流时互相影响。

验证：

- 三路按顺序启动后能持续显示。
- 内核日志没有持续的 CSI timeout。

### 问题 5：MAX96724 C/D link 带宽设置时 reset link 位可能错

现象：

- 某些 link 配置时，A/B 正常，但 C/D 相关链路容易异常。

原因：

- `z_max96724_set_link_bandwidth()` 里原逻辑为了选择寄存器，会在 `link >= 2` 时修改 `link` 变量。
- 后续如果直接用修改后的 `link` 去写 `0x0018` reset 位，C/D 可能被当成 A/B 去 reset。

解决：

- 增加 `reset_link = link` 保存原始 link。
- 选择寄存器时可以修改临时 `link`，但写 reset 位时使用 `reset_link`。

当前关键逻辑：

```c
int reset_link = link;
...
if (link >= 2) {
    reg++, link -= 2;
}
...
max96724_write_reg(dev, 0x0018, (1 << reset_link));
```

验证：

- A/B/C 三路都能在 media graph 中出现并出图。

### 问题 6：A/B 共用 CSI controller 时 VC 必须分开

现象：

- 多路都映射到同一个 CSI controller、同一个 VC 时，画面会冲突或某一路没有数据。

原因：

- Jetson VI/NVCSI 依赖 virtual channel 区分同一 CSI controller 上的不同视频流。
- A/B 如果都进入 `dst-csi-ctrl=1`，就不能都用相同 `dst-vc`。

解决：

- A：`dst-vc = 0`。
- B：`dst-vc = 1`。
- 两路都进入 `dst-csi-ctrl = 1`。

验证：

- `media-ctl -p` 能看到三路 endpoint 全部 enabled。
- `/dev/video1`、`/dev/video2` 都能出图。

### 问题 7：C 路需要走另一个 CSI controller

现象：

- 当所有路都按同一个 CSI 输出配置时，第三路不稳定或无图。

原因：

- 当前硬件两根 CSI 都接到了 Jetson。
- 三路里 C 路被安排到另一个 CSI controller。

解决：

- C 路配置为：

```text
port-index = <1>
bus-width = <2>
dst-csi-ctrl = <2>
dst-vc = <0>
```

验证：

- `/dev/video0` 对应的 `9-0012` 能出图。

### 问题 8：C 路 lane polarity 不对会影响画面

现象：

- C 路调试过程中需要尝试 lane polarity。

原因：

- Jetson CSI lane 极性和板级走线有关。
- C 路所在 CSI 口和 A/B 不完全一样。

解决：

- 在 C 路 module 配置中加入：

```text
lane_polarity = "6";
```

验证：

- 保留了 `g010_lanepol6_uyvy_30.raw` 作为验证抓帧。
- C 路最终能正常显示。

### 问题 9：`/dev/video0/1/2` 顺序不是物理口顺序

现象：

- 用户看到 `/dev/video0`、`/dev/video1`、`/dev/video2`，容易认为它们一定对应 A/B/C。

原因：

- Jetson media graph 的 video node 顺序由 device tree、probe 顺序、VI channel 注册顺序决定。
- 它不一定等于解串板丝印 A/B/C 顺序。

解决：

- 用 `media-ctl -p -d /dev/media0` 查看真实映射。

当前看到：

```text
/dev/video0 <- z_g010_sc235_96717 9-0012
/dev/video1 <- z_g010_sc235_96717 9-0011
/dev/video2 <- z_g010_sc235_96717 9-0010
```

验证：

- 三个节点都能显示。
- 如果后续要严格命名物理 A/B/C，需要遮挡每个镜头再修正脚本标签。

### 问题 10：只接一根 CSI 线时不能完成当前三路方案

现象：

- 当前设计里 A/B 和 C 分到两个 CSI controller。
- 如果只接一根 CSI 线，三路不能全部正常进入 Jetson。

原因：

- C 路走 `dst-csi-ctrl=2`，不是和 A/B 完全同一路 CSI。

解决：

- 两个 CSI 接口都接在解串板上。

验证：

- 两根 CSI 都接好后，三路 `/dev/video*` 节点存在并能出图。

### 问题 11：三路同时全速取流会导致设备卡死

现象：

- 用户反馈“三路同时取流，这个设备会卡死”。

原因：

- 早期测试直接三路并行启动，并且显示端不降帧。
- Jetson 的 VI/NVCSI、NVMM 转换、OpenGL 显示同时承压。
- 驱动 stream-on 阶段如果还重配 MIPI TX/PHY，更容易在多路并发时卡死。

解决：

- 默认不走三路完全并发启动。
- `show_g010_3cams.sh` 默认三路窗口模式，按 `START_DELAY=5` 秒错峰启动。
- 显示端默认 `DISPLAY_FRAMERATE=5/1`，只降低显示帧率，不降低相机采集帧率。
- `check_g010_3cams.sh` 默认 `MODE=safe`，只做逐路验证。
- 三路全并发 fakesink 测试必须显式指定 `MODE=parallel`，避免误触发卡死路径。

验证：

- 三路显示服务运行时，三个 Python 进程都在。
- 画面右上角显示 `CAP 30 fps`、`DISP 5 fps`。

### 问题 12：MAX96724 stream-on 阶段重置 MIPI TX/PHY 会影响并发

现象：

- 三路打开时，如果某一路 stream-on 过程中重配 MIPI TX 或 reset PHY，其他已经打开或正在等待帧的 VI channel 可能受影响。

原因：

- MAX96724 是多路共享解串器。
- MIPI TX mode 和 PHY reset 是全局/半全局性质的动作，不适合每个 V4L2 open 都重复做。

解决：

- `z_max96724_start_streaming()` 中保留 pipe 映射和 pipe enable。
- 不再在 stream-on 阶段写 MIPI TX10 相关寄存器。
- 不再在 stream-on 阶段 reset PHY。
- PHY/MIPI 基础状态放在 probe 初始化阶段。

当前关键逻辑：

```c
max96724_read_reg(dev, 0xf4, &val);
max96724_write_reg(dev, 0xf4, (val | (1 << g_ctx->des_link)) & 0xff);
```

验证：

- 三路错峰启动后稳定显示。
- 内核日志没有持续 `timeout`。

### 问题 13：stop-streaming 时不能随便关闭所有 GMSL link

现象：

- 某一路关闭时，如果把解串器所有 link 都复位，其他路画面会受影响。

原因：

- 多路相机共享同一颗 MAX96724。
- 单路 stop 不应该破坏其他路正在使用的配置。

解决：

- `z_max96724_stop_streaming()` 只清当前 link 的 pipe enable bit。
- 当所有 pipe 都停止时，也保持 GMSL link 配置，不写 `0x0018 = 0x0f` 这类全链路 reset。

当前日志：

```text
zuojisi: all stopped, keep GMSL links configured
```

验证：

- 单路关闭不会强制打断其他路配置。

### 问题 14：三路测试脚本不能默认做危险的 parallel 测试

现象：

- 早期为了验证三路，会自然想到直接三个 `v4l2src` 并在一个 pipeline 里跑。
- 但该路径曾导致设备卡死。

原因：

- 这会同时打开三个 VI channel、同时启用三个 GMSL pipe、同时做 NVMM 转换。
- 对当前驱动和硬件状态来说风险高。

解决：

- `check_g010_3cams.sh` 默认：

```bash
MODE=safe
```

- safe 模式逐个相机取帧。
- parallel 模式保留，但必须显式启用：

```bash
MODE=parallel ./g010_adapt/check_g010_3cams.sh
```

验证：

- 多轮逐路 30 帧测试通过。
- 两两并发测试通过。
- 三路显示走错峰启动，不走危险的全速 parallel 检查。

### 问题 15：三路全速显示资源压力太高

现象：

- 即使相机采集本身能到 30fps，三个窗口全速渲染也可能让系统负载过高。

原因：

- 三路 1600x1200 30fps 数据量较大。
- 显示链路包含 `nvvidconv`、NVMM、OpenGL sink。
- Jetson 桌面环境本身也占用 GPU/CPU。

解决：

- 相机采集保持 `SOURCE_FRAMERATE=30/1`。
- 显示端通过 `videorate drop-only=true` 限为 `DISPLAY_FRAMERATE=5/1`。

当前 pipeline 思路：

```text
v4l2src -> UYVY 1600x1200@30 -> videorate drop-only -> display 5fps -> textoverlay -> nvvidconv -> nveglglessink
```

验证：

- 画面右上角显示：

```text
CAP 30.0 fps
DISP 5.0 fps
```

### 问题 16：需要看真实采集帧率，不只是窗口显示是否流畅

现象：

- 用户需要确认帧率。
- 只看窗口感觉不准确，因为显示端已经限帧。

原因：

- 当前为了稳定，显示帧率和采集帧率是两个不同概念。

解决：

- 新增 Python GStreamer 脚本 `show_g010_camera_fps.py`。
- 在 `v4l2src` 后加 `identity name=src_counter` 统计采集帧。
- 在 `videorate` 后加 `identity name=disp_counter` 统计显示帧。
- 用 `textoverlay` 在画面右上角叠加：

```text
CAP xx.x fps
DISP xx.x fps
```

验证：

- 当前截图显示三路 `CAP` 约 30fps，`DISP` 约 5fps。

### 问题 17：`gst-launch-1.0` 不方便动态更新 FPS 文本

现象：

- 如果只用 shell 里的 `gst-launch-1.0`，可以显示画面，但不方便每秒动态更新右上角文字。

原因：

- `textoverlay text=...` 可以设置静态文字，但动态修改属性需要程序控制。

解决：

- 改用 Python GI/GStreamer。
- 程序里每秒计算 FPS，并调用：

```python
overlay.set_property("text", ...)
```

验证：

- 三路窗口右上角 FPS 每秒刷新。

### 问题 18：`nveglglessink` 会打印误导性的 GStreamer-CRITICAL

现象：

手动运行脚本时，终端出现：

```text
GStreamer-CRITICAL **: gst_mini_object_copy: assertion 'mini_object != NULL' failed
GStreamer-CRITICAL **: gst_caps_get_structure: assertion 'GST_IS_CAPS (caps)' failed
GStreamer-CRITICAL **: gst_structure_copy: assertion 'structure != NULL' failed
GStreamer-CRITICAL **: gst_caps_append_structure_full: assertion 'GST_IS_CAPS (caps)' failed
```

原因：

- 用 `videotestsrc + nveglglessink` 也能复现同样日志。
- 因此这不是相机、解串板、CSI 或三路驱动错误。
- 它是 NVIDIA `nveglglessink` 初始化阶段的日志噪声。

解决：

- 在 `show_g010_camera_fps.py` 中新增 `set_playing_quietly()`。
- 默认只在 `pipeline.set_state(Gst.State.PLAYING)` 和短暂 `get_state()` 阶段临时把 stdout/stderr 指到 `/dev/null`。
- 后续真正的 GStreamer bus error 仍会打印：

```text
GStreamer error: ...
```

如果确实要看初始化噪声，可以设置：

```bash
SHOW_GST_INIT_LOGS=1 ./g010_adapt/show_g010_3cams.sh
```

验证：

- 短时间启动验证不再刷这组 `GStreamer-CRITICAL`。
- 三路画面仍正常。

### 问题 19：重复运行脚本会留下旧窗口和旧进程

现象：

- 终端里运行一次脚本后，再运行第二次，可能看到多个窗口。
- 也可能误以为新脚本还在打印旧日志。

原因：

- 手动前台运行的 `show_g010_3cams.sh` 会启动三个子进程。
- 如果没有正确停止，旧 Python 进程仍然占用设备或留在桌面上。

解决：

- 补充 `stop_g010_camera.sh`。
- 停止用户 systemd 服务：

```bash
systemctl --user stop g010-3cams.service
```

- 同时清理本项目的相机显示进程。

验证：

- `pgrep -af 'show_g010|gst-launch|python3 .*show_g010|g010-3cams'` 不再看到旧实例。

### 问题 20：原停止脚本只杀 `gst-launch-1.0`，停不掉 Python FPS 版本

现象：

- 改成 Python FPS 叠加后，原停止脚本无效。

原因：

- 原脚本只有：

```bash
pkill -x gst-launch-1.0
```

- 但当前显示进程是 `python3 show_g010_camera_fps.py`。

解决：

- 修改 `stop_g010_camera.sh`：

```bash
systemctl --user stop g010-3cams.service 2>/dev/null || true
pkill -x gst-launch-1.0 2>/dev/null || true
pkill -f "${SCRIPT_DIR}/show_g010_camera_fps.py" 2>/dev/null || true
```

验证：

- 停止脚本能清理当前三路显示服务和 Python 显示进程。

### 问题 21：不能用过宽的 `pkill -f`

- 如果外层 shell 命令行里也包含匹配字符串，就可能误杀自己。

### 问题 25：`corr_err: discarding frame 0` 容易被误判为严重错误

现象：

内核日志里偶尔出现：

```text

```

原因：

- 这些日志出现在启动瞬间。
- 没有持续出现 `timeout`、`CHANSEL`、`CSIMUX`。
- 一般表示启动过程中丢了第一帧或少量帧，不代表稳定运行失败。

解决：

- 判断是否严重时看是否持续报错。
- 重点查：

```text
timeout
CHANSEL
CSIMUX
uncorr
```

验证：

- 当前日志只有启动瞬间少量 `corr_err`。
- 三路画面持续显示。

### 问题 26：`Using winsys: x11` 不是错误

## 9. 结论

这次适配的核心不是简单写一个显示脚本，而是把整条链路打通：

```text
Device Tree 三路拓扑
-> MAX96724 / MAX96717 驱动映射
-> VC / CSI controller / lane polarity
-> V4L2 节点注册
-> UYVY 取流
-> GStreamer/NVMM 显示
-> 三路错峰启动
-> 显示限帧
-> FPS 叠加
```

最终可用方案是：

- 驱动层避免多路 stream-on 时重置共享 MIPI/PHY；
- DTS 层明确三路 VC 和 CSI controller；
- 用户态脚本层用错峰启动和显示限帧保证稳定；
- FPS 叠加同时展示采集帧率和显示帧率；
- 停止脚本负责清理 systemd 服务和 Python/GStreamer 进程。

当前稳定优先配置是三路采集约 30fps、三路显示 5fps。这个配置已经能满足三路同时预览，同时避开之前三路全速显示导致设备卡死的问题。
